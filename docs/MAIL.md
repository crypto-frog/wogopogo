# Wogopogo contact and submission notifications

## Contact

`hello@wogopogo.ca` is the website contact and moderation-notification destination.
It is a Zoho alias on the owner's existing Canadian-region inbox. The primary
mailbox identity remains unchanged. Use Zoho webmail's Wogopogo From address for
replies. No new paid seat, OAuth grant or autonomous reply authorization is needed.

The shared mail broker has an explicit **owner-only** route, change 051 on
[agent-ops/feature/wogopogo-mail-051](https://github.com/crypto-frog/agent-ops/tree/feature/wogopogo-mail-051).
Employer correspondence must not enter the Annapants game-support model workflow.
Keep actual account IDs, grants, mail bodies, DNS receipts and backups private.

## Submission flow

1. The public form validates the job and creates a pending listing.
2. The same database transaction records a notification in `submission_notifications`.
3. The private one-minute worker hands a plain-text review email to Bluehost's MTA,
   addressed to the Zoho contact. Public requests do not wait for mail delivery.
4. The email includes submitted fields and `/admin?job=ID`. Admin authentication and
   an explicit approval are still required. Tokens and the admin key are never emailed.
5. The admin screen highlights and expands the selected pending listing.

Imports do not generate submission emails. Already moderated, removed or non-public
records cancel their pending notifications. Applicant-controlled data stays in the
body; addresses, envelope sender, subject and Message-ID are generated by the server.
The form explains that its contents are emailed to the reviewer through Zoho.

## Configuration and scheduling

The public template defaults to disabled. Only the server-side configuration enables:

```php
'submission_notifications' => [
    'enabled' => true,
    'to' => 'hello@wogopogo.ca',
    'from' => 'hello@wogopogo.ca',
],
```

Install `ops/wogopogo.php` and `ops/notify-submissions.sh` together in
`~/wogopogo_ops`, mode 700, outside the web root. Add one scoped crontab entry:

```cron
* * * * * /bin/bash "$HOME/wogopogo_ops/notify-submissions.sh" >/dev/null 2>&1
```

Preserve unrelated crontab entries. The runner uses an account-private lock, a bounded
batch of ten and a 60-second timeout. Its latest success/error receipts replace previous
receipts, so ordinary cron output does not create an unbounded log. Inspect receipt
modification times and `notification:status` during maintenance; an old error receipt
is historical if a newer success exists. A rollback to a pre-outbox release pauses the
runner and preserves queued notifications for a corrected release.

## Delivery and recovery

```sh
php ~/wogopogo_ops/wogopogo.php notification:status
php ~/wogopogo_ops/wogopogo.php notification:send --limit 10 \
  --apply --actor agent:mail-maintenance --reason 'Reviewed due owner notifications'
```

`sent` means the local MTA accepted the message, not independently confirmed inbox
arrival. Confirm initial production delivery in Zoho and inspect the host mail trace
when investigating delivery. Do not blindly resend accepted messages.

Explicit transport refusal retries with backoff, at most five attempts. Exceptions or
an interrupted handoff become `unknown`; they may already have delivered. Inspect Zoho
and delivery records before using `notification:resolve --id ID --resolution sent|retry`,
with the required `--apply --actor --reason`. Resolution is private, audited and never
available through a public URL. Stale `sending` records are held after ten minutes.

DNS includes Canadian Zoho MX, a single combined Zoho/Bluehost SPF record, Zoho
2048-bit DKIM selector `wogo202609` and monitoring-mode DMARC. Bluehost's existing
DKIM and sending authorization are retained for application notifications. The domain
uses Remote mail routing; there was no Wogopogo mailbox or forwarder to migrate.
Website addresses, nameservers, other domains and existing mail routes are preserved.
